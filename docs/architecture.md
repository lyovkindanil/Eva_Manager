# Архитектура

## Компоненты

**eva-manager** — один статический бинарник на Go. Внутри веб-интерфейс
(React, собирается в `internal/web/dist` и встраивается через `embed`),
HTTP API и всё управление ядром. Работает от отдельного пользователя, не от
root; файлы данных создаются с правами 0600.

**Xray-core** — дочерний процесс панели. Конфиг панель пишет сама в
`$EVA_DATA_DIR/xray/config.json`. Управление идёт через gRPC API Xray на
127.0.0.1 (`EVA_XRAY_API`): адрес вне loopback панель не примет, потому что
API добавляет и удаляет пользователей без пароля.

**База** — SQLite по умолчанию (одна служба меньше, бэкап одним файлом) или
PostgreSQL (`EVA_DATABASE_URL=postgres://…`) для сервиса с продажей доступа и
десятков узлов.

## Конфиг Xray

1. Новый конфиг пишется во временный файл и проверяется `xray run -test`.
   Отвергнутый конфиг не записывается и не трогает работающий Xray
   (`xray.Test`, `Process.Restart`).
2. Проверенный конфиг атомарно заменяет рабочий, Xray запускается. Если
   процесс упал в первые 1,5 секунды (например, порт занят), ошибка с
   выводом Xray возвращается сразу.
3. Упавший Xray панель перезапускает с паузой от 1 до 30 секунд и показывает
   причину в интерфейсе.

На этапе 1 к этому добавятся версии конфига в `config_versions` и откат на
прошлую версию, если новая не поднялась.

`xray.BaseConfig` — минимальный конфиг: API (`HandlerService`,
`StatsService`, `LoggerService`), статистика по пользователям на уровне 0,
выход `direct` и блокировка частных сетей. Инбаунды пользователей добавит
сборщик конфига.

## База

Схема — `internal/db/migrations/NNNN_имя.sql`, одна для обеих баз: общее
подмножество SQL (идентификаторы TEXT, время BIGINT в секундах Unix, без
AUTOINCREMENT и SERIAL). Запросы пишутся с `?` и для PostgreSQL
переписываются в `$1, $2…` (`DB.Rebind`). Каждая миграция идёт в своей
транзакции; упавшая не оставляет схему наполовину изменённой. Если схема в
базе новее сборки, панель не стартует.

Тесты гоняются на обеих базах (`dbtest.Each`): в CI — SQLite и PostgreSQL 16.

## Узлы

Таблица `nodes` есть с первого дня: свой сервер панель ведёт как локальный
узел (`is_local`). На этапе 4 остальные серверы подключатся агентом — тем
же бинарником в режиме узла, по mTLS — без изменения схемы.

## HTTP API

| Метод | Что отдаёт |
|---|---|
| `GET /api/health` | `{"status":"ok"}`, если база отвечает |
| `GET /api/status` | Версия панели, база и схема, состояние Xray, узлы |
| `GET /api/xray/logs` | Последние 500 строк вывода Xray |

Остальные пути отдают интерфейс; неизвестный путь без расширения — его
маршрут, на него приходит `index.html`.
