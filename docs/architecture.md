# Архитектура

## Компоненты

**eva-manager** — один статический бинарник на Go. Внутри веб-интерфейс
(React, собирается в `internal/web/dist` и встраивается через `embed`),
HTTP API и всё управление ядром. Работает от отдельного пользователя, не от
root; файлы данных создаются с правами 0600.

**Xray-core** — дочерний процесс панели. Конфиг панель пишет сама в
`$EVA_DATA_DIR/xray/config.json`. Управление идёт через gRPC API Xray на
127.0.0.1 (`EVA_XRAY_API`): адрес вне loopback панель не примет, потому что
API добавляет и удаляет пользователей без пароля.

**AmneziaWG** — по дочернему процессу `eva-manager awg-run` на интерфейс
(awg0, awg1…): тот же бинарник, внутри amneziawg-go. Процесс создаёт
интерфейс, ставит адрес и правила NAT и открывает UAPI-сокет
`/var/run/amneziawg/<iface>.sock` (`EVA_AWG_SOCKET_DIR`) — тот же, что
читает штатный `awg show`. Ключи и пиры процесс на диск не пишет: их
присылает панель. Подробнее — раздел «AmneziaWG».

**База** — SQLite по умолчанию (одна служба меньше, бэкап одним файлом) или
PostgreSQL (`EVA_DATABASE_URL=postgres://…`) для сервиса с продажей доступа и
десятков узлов.

## Конфиг Xray

1. Новый конфиг пишется во временный файл и проверяется `xray run -test`.
   Отвергнутый конфиг не записывается и не трогает работающий Xray
   (`xray.Test`, `Process.Restart`).
2. Проверенный конфиг атомарно заменяет рабочий, Xray запускается. Если
   процесс упал в первые 1,5 секунды (например, порт занят), ошибка с
   выводом Xray возвращается сразу.
3. Упавший Xray панель перезапускает с паузой от 1 до 30 секунд и показывает
   причину в интерфейсе.

На этапе 1 к этому добавятся версии конфига в `config_versions` и откат на
прошлую версию, если новая не поднялась.

`xray.BaseConfig` — минимальный конфиг: API (`HandlerService`,
`StatsService`, `LoggerService`), статистика по пользователям на уровне 0,
выход `direct` и блокировка частных сетей. Инбаунды пользователей добавляет
`inbound.BuildConfig`.

## Инбаунды

Инбаунд хранится в базе как типизированная структура
(`internal/inbound`): VLESS Reality на tcp (xtls-rprx-vision) с опцией
VLESS Encryption (mlkem768x25519plus). Из модели одна функция строит
фрагмент конфига Xray (`ConfigFragment`), другая — ссылку vless://
(`Link`): сырой JSON не редактируется, поэтому конфиг и ссылка не могут
разойтись. Приватные ключи (Reality, ML-KEM-768) генерирует панель,
публичные для ссылки выводятся из них. Пользователей в конфиг не пишем:
они добавляются в работающее ядро через gRPC API.

Ссылки проверяются парсером самого VPN4Eva: копия
`core/internal/profile/vless.go` клиента лежит в
`internal/testutil/vpn4eva` и обновляется `scripts/sync-vpn4eva-parser.sh`
до закреплённого коммита (репозиторий клиента приватный, источник —
локальный клон в `VPN4EVA_SRC` или учётные данные git). В CI сгенерированный
конфиг дополнительно прогоняется через `xray run -test` закреплённой
версии ядра.

Сам клиент VPN4Eva проверяет ссылку в `internal/e2e/vpn4eva_test.go`:
`vpn4eva-bench` из репозитория клиента (тот же пропатченный sing-box, что
в приложении, только вместо TUN — SOCKS) подключается по ссылке панели к
Xray панели, с VLESS Encryption и без. Бинарник собирается из приватного
репозитория, поэтому тест идёт локально (`EVA_TEST_VPN4EVA_BENCH`), а в CI
пропускается.

## AmneziaWG

Интерфейс в базе (`awg_interfaces`) — ключ сервера, порт, подсеть
клиентов (по умолчанию 10.8.0.0/24, сервер — первый адрес), MTU, DNS и
маскировка AmneziaWG 2.0: Jc/Jmin/Jmax, S1–S4 и непересекающиеся
диапазоны H1–H4 (случайные при создании, в пределах, которые выбирает
приложение AmneziaVPN; проверка — по правилам клиента VPN4Eva). Пир
(`awg_peers`) — пользователь на интерфейсе: свой ключ, общий ключ (PSK) и
адрес. Пиры выдаются сразу всем пользователям при создании интерфейса и
каждому новому пользователю; выключение пользователя пир не удаляет, только
убирает с сервера — включённый получит ту же конфигурацию.

Из одной модели строятся:

- настройки сервера для UAPI (`Interface.DeviceUAPI`);
- файл клиента в формате awg-quick (`ClientConf`) — `eva-manager user conf`;
- ключ `vpn://` (`VPNKey`) — формат приложения AmneziaVPN, base64url от
  qCompress JSON с контейнером `amnezia-awg`; он же идёт в подписку.

Тесты разбирают оба варианта копией парсера VPN4Eva, а клиент
amneziawg-go с настройками из разобранной конфигурации обменивается
данными с сервером — маскировка обеих сторон совпадает.

Работа на узле (`awg.Manager`):

1. Сборщик (`panel.SyncUsers`, раз в 30 секунд и по `eva-manager apply`)
   запускает процессы включённых интерфейсов и останавливает лишние.
   Смена имени, подсети или MTU — перезапуск процесса; порт, ключи и
   маскировка применяются на лету.
2. После каждого запуска панель присылает полные настройки и пиры
   активных пользователей (`PushAWG`). Упавший процесс перезапускается
   с паузой 1–30 секунд.
3. Дальше пиры сверяются разницей: недостающие добавляются, лишние
   (выключенные, истёкшие, с исчерпанным лимитом) убираются — сессии
   остальных не рвутся.
4. Трафик — счётчики `rx_bytes`/`tx_bytes` пиров из UAPI. Они растут с
   запуска устройства, поэтому панель хранит прошлые значения и пишет
   приращения; после перезапуска процесса отсчёт с нуля. Трафик
   AmneziaWG и Xray складывается в общий счётчик пользователя, лимит
   считается по сумме.

Сеть: процесс включает `net.ipv4.ip_forward` (если может; в Docker его уже
включил сам Docker) и ставит правила iptables с тем бэкендом, в котором у
системы больше правил (nft или legacy — иначе политика FORWARD DROP от
Docker или ufw их бы не увидела): MASQUERADE для подсети, разрешения в
FORWARD, запрет клиент↔клиент и запрет частных сетей за сервером
(локальная сеть, `169.254.169.254` облаков) — как у Xray с
`defaultBlockPrivateRule`. При остановке правила снимаются; оставшиеся от
убитого процесса не дублируются. IPv6 клиентам не выдаётся, но
`AllowedIPs` включает `::/0`: IPv6-трафик уходит в туннель и не течёт
мимо него.

Права: создать интерфейс и правила может только процесс с
`CAP_NET_ADMIN`. В Docker-образе права есть только у `eva-awg` — копии
бинарника с `setcap` (и у iptables); сама панель запускается без них,
поэтому образ работает и без `cap_add`, а AmneziaWG без прав сообщает,
чего не хватает.

## База

Схема — `internal/db/migrations/NNNN_имя.sql`, одна для обеих баз: общее
подмножество SQL (идентификаторы TEXT, время BIGINT в секундах Unix, без
AUTOINCREMENT и SERIAL). Запросы пишутся с `?` и для PostgreSQL
переписываются в `$1, $2…` (`DB.Rebind`). Каждая миграция идёт в своей
транзакции; упавшая не оставляет схему наполовину изменённой. Если схема в
базе новее сборки, панель не стартует.

Тесты гоняются на обеих базах (`dbtest.Each`): в CI — SQLite и PostgreSQL 16.

## Узлы

Таблица `nodes` есть с первого дня: свой сервер панель ведёт как локальный
узел (`is_local`). На этапе 4 остальные серверы подключатся агентом — тем
же бинарником в режиме узла, по mTLS — без изменения схемы.

## HTTP API

| Метод | Что отдаёт |
|---|---|
| `GET /api/health` | `{"status":"ok"}`, если база отвечает |
| `GET /api/status` | Версия панели, база и схема, состояние Xray и интерфейсов AmneziaWG, узлы |
| `GET /api/xray/logs` | Последние 500 строк вывода Xray |

Остальные пути отдают интерфейс; неизвестный путь без расширения — его
маршрут, на него приходит `index.html`.
